# MatchCraft — Security Audit & Hardening Report

**Scope:** v1 (web app + Cloudflare Worker), v2 (iOS keyboard extension + Android IME), v3 (Android floating overlay).
**Date:** 2026-09-18

> **Read this first.** This audit closes the common, known classes of issues that a
> pentester or app-store reviewer checks for. It is **not** a guarantee of security and
> should not be described as one. Before a wide public launch, get a professional
> penetration test or an independent human security review. Several residual risks
> below cannot be closed without user accounts, which are out of scope for v1–v3.

---

## 1. Secrets and credentials

### ✅ No secrets were ever committed — **no key rotation required**

Scanned **every blob in every commit on every branch**, not just current files:

```bash
# Every file ever added, across all branches
git log --all --pretty=format: --name-only --diff-filter=A | sort -u

# Content scan of every historical commit
for rev in $(git rev-list --all); do
  git grep -I -nE 'sk-ant-[A-Za-z0-9_-]{10,}|sk-[A-Za-z0-9]{32,}|AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{36}|-----BEGIN [A-Z ]*PRIVATE KEY-----' $rev
  git grep -I -niE '(api[_-]?key|secret|token|password|credential)\s*[:=]\s*["'"'"'][^"'"'"']{8,}' $rev
done
```

Both scans returned **zero matches**. No `.env`, `.dev.vars`, keystore, or
`google-services.json` file has ever existed in the history. The only env files
tracked are `worker/.env.example` and `frontend/.env.example`, which contain the
literal placeholder `sk-ant-...` and a placeholder URL.

The Claude API key is referenced **only** as `env.CLAUDE_API_KEY` inside
`worker/src/index.js` and is set via `wrangler secret put`. It appears in no
frontend, iOS, or Android code path — verified by grep across all branches.

| # | Finding | Severity | Status |
|---|---------|----------|--------|
| S-1 | API key in git history | — | **Not present.** No rotation needed. |
| S-2 | API key in client code | — | **Not present.** Worker-only. |
| S-3 | `.gitignore` missed mobile secret classes | **Medium** | **Fixed** |

**S-3 detail.** The original `.gitignore` covered `.env`, `.dev.vars`, `node_modules/`,
`dist/`. It did **not** cover the file types that leak secrets in mobile repos — so as
soon as someone opened the Android project in Android Studio or built a signed APK,
a `git add -A` would have committed them. Added:

- `local.properties` (absolute SDK paths / occasionally tokens)
- `*.keystore`, `*.jks`, `keystore.properties` — **release signing keys**
- `google-services.json`
- `*.mobileprovision`, `*.p12`, `*.cer` — iOS signing identities
- `.gradle/`, `build/`, `captures/`, `*.apk`, `*.aab`
- `xcuserdata/`, `DerivedData/`, `Pods/`, `*.xcworkspace/`
- `*.xcodeproj/` (generated by XcodeGen from `project.yml` — should never be tracked)
- Broadened `.env` → `.env.*` with a `!.env.example` negation

## 2. Backend (Cloudflare Worker) hardening

All findings below are **fixed** in `worker/src/index.js`. A regression suite covering
every one of them lives at `worker/test/security.test.mjs` (`npm test` — 26 assertions,
all passing).

### W-1 — CORS was fully open to every origin — **HIGH** — Fixed

```js
// BEFORE
const CORS = { 'Access-Control-Allow-Origin': '*', ... }
```

Any website on the internet could invoke the endpoint from a visitor's browser and
spend your Claude credits. Replaced with an env-driven exact-match allowlist
(`ALLOWED_ORIGINS` in `wrangler.toml`). A non-allowlisted `Origin` now receives
**no** `Access-Control-Allow-Origin` header, so the browser blocks the response.
Added `Vary: Origin` so caches don't serve one origin's CORS decision to another.

**Important caveat, stated plainly:** CORS constrains *browsers only*. It is not
authentication and does nothing against `curl`, a script, or a native app — none of
which enforce it. The actual spend protection is W-3/W-4 below. Do not treat the CORS
fix as an access control.

### W-2 — Validation bypass via prototype chain → prompt injection — **HIGH** — Fixed

```js
// BEFORE
if (!tone || !TONE_PROMPTS[tone]) return json({ error: 'Invalid tone' }, 400)
```

A bare `OBJ[key]` truthiness test also matches **inherited** members. Verified
empirically:

| `tone` value | Passed validation? | Interpolated into the system prompt as |
|---|---|---|
| `constructor` | **yes** | `function Object() { [native code] }` |
| `toString` | **yes** | `function toString() { [native code] }` |
| `valueOf` | **yes** | `function valueOf() { [native code] }` |
| `hasOwnProperty` | **yes** | `function hasOwnProperty() { [native code] }` |
| `__proto__` | **yes** | `[object Object]` |

The value lands directly inside the system prompt (`The tone should be ${TONE_PROMPTS[tone]}.`),
letting a caller corrupt the instruction block. Same flaw on `mode` and `platform`.

Fixed with explicit `Array.includes()` allowlists plus a `typeof === 'string'` guard.
`platform` — genuinely optional — is now silently dropped when unrecognised rather
than rejected.

### W-3 — Rate limiting failed **open** when KV was unbound — **HIGH** — Fixed

```js
// BEFORE
if (env.RATE_LIMIT_KV) { /* ...entire rate limit... */ }
```

`wrangler.toml` ships with the KV block **commented out**. Anyone deploying without
carefully reading the comments got a worker with **no spend controls whatsoever** —
and no error, no warning, no log line. Silent failure of a security control on the
default path.

Now **fails closed**: an unbound namespace returns `503` for every request. Local
development can opt out explicitly with `ALLOW_UNLIMITED = "true"`, which is
documented as never-in-production.

### W-4 — Rate limit keyed off a spoofable client header — **HIGH** — Fixed

```js
// BEFORE
const ip = request.headers.get('CF-Connecting-IP')
  || request.headers.get('X-Forwarded-For')?.split(',')[0]?.trim()
  || 'unknown'
```

`X-Forwarded-For` is fully attacker-controlled. Any caller reaching the worker on a
path where `CF-Connecting-IP` is absent gets an unlimited number of fresh rate-limit
buckets by varying one header — a complete bypass. Removed the fallback entirely;
`CF-Connecting-IP` is set by Cloudflare itself and strips any client-supplied copy.
Unidentified callers now share a single `noip` bucket instead of each getting a fresh
allowance. Regression-tested.

### W-5 — No size ceiling on `imageBase64` — **HIGH** — Fixed

The image string was passed straight to the Claude API with no length check. A single
request carrying a ~100 MB base64 blob could exhaust the Worker's 128 MB memory limit,
and — more expensively — a stream of large images bills unbounded input tokens against
your key. Added:

- `Content-Length` pre-check rejecting >8 MB **before** the body is read into memory
- `imageBase64.length` capped at ~6.99 M chars (= Anthropic's 5 MB image limit)
- A base64 charset regex, rejecting non-base64 junk before it reaches the upstream call
- Body-shape validation rejecting arrays and non-objects

Returns `413` with a user-friendly message.

### W-6 — Quota consumed before input validation — **Medium** — Fixed

Rate-limit increment ran *before* body parsing, so malformed requests burned a real
user's daily allowance — a trivial griefing vector against a shared NAT/office IP.
Reordered: validate (free, no upstream cost) → check and increment quota → call Claude.

### W-7 — Upstream error bodies written to logs — **Medium** — Fixed

```js
// BEFORE
console.error('Claude API error:', claudeResp.status, errText)
console.error('Claude fetch error:', err)
```

`errText` is the raw upstream response body, and `err` can carry request context.
Both land in Cloudflare's log stream. Replaced with status-code-only structured tokens
(`upstream_error_status 502`). Client-facing messages were already generic and remain
so — verified by test that a simulated upstream 500 containing a fake path, stack
trace, and `sk-ant-` string leaks **none** of it to the caller.

### W-8 — No abuse ceiling across rotating IPs — **High** — Fixed (partially; see residual risk)

See §6.

### W-9 — Missing hardening response headers — **Low** — Fixed

Added `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` to all
responses. `OPTIONS` now correctly returns `204`.

### ✅ Confirmed clean (no change needed)

- **No image or conversation content is logged.** No `console.log` of `imageBase64`,
  `suggestions`, or `rawText` exists anywhere in the worker.
- **`max_tokens: 1024`** already bounds worst-case output cost per request.
- **Error responses never contained stack traces or upstream text** — every client-facing
  error is a hand-written generic string.

## 4. Mobile-specific (v2 and v3)

### ✅ M-1 — Keyboards genuinely never read typed content — **verified in code**

This is the claim that matters most, so it was checked against the implementation
rather than the marketing copy. Both keyboards only ever **write**:

| Platform | Every text-field interaction in the codebase |
|---|---|
| iOS `KeyboardViewController.swift` | `textDocumentProxy.insertText()` (line 441), `textDocumentProxy.deleteBackward()` (line 355) |
| Android `MatchCraftIME.kt` | `currentInputConnection?.commitText()` (line 220), `deleteSurroundingText()` (line 140) |

There is **no** call to `documentContextBeforeInput`, `documentContextAfterInput`,
`getTextBeforeCursor`, `getTextAfterCursor`, `getSelectedText`, or `getExtractedText`,
and **no** `onUpdateSelection` override anywhere. The apps are structurally incapable of
reading the user's typing as written. Combined with zero logging calls (`Log.*`,
`println`, `NSLog`, `os_log`, `print` — all absent from both apps) and zero persistence
in those packages, the privacy claim holds.

### ✅ M-2 — No TLS bypass anywhere — **verified**

Grepped both apps for every common certificate-validation-disabling pattern:
`NSAllowsArbitraryLoads`, `NSExceptionAllowsInsecureHTTPLoads`,
`URLAuthenticationChallenge` / `didReceiveChallenge`, `serverTrust`,
`X509TrustManager`, `HostnameVerifier`, `sslSocketFactory`, `TrustAllCerts`.
**Zero matches.** Both clients use the platform default TLS stack with full validation.
No ATS exception dictionary exists in either `Info.plist`.

### M-3 — Android `usesCleartextTraffic` left to platform default below API 28 — **Medium** — Fixed *(v2, v3)*

```xml
<!-- BEFORE -->
<network-security-config>
    <domain-config cleartextTrafficPermitted="false">
        <domain includeSubdomains="true">workers.dev</domain>
    </domain-config>
</network-security-config>
```

There was no `<base-config>`. `minSdk` is **26**, and on API 26–27 the platform default
for `cleartextTrafficPermitted` is **`true`** — so on Android 8.0/8.1 the app permitted
plaintext HTTP to every domain other than `workers.dev`. The config also silently
stopped applying if the worker were deployed to a custom domain. Added a global
`<base-config cleartextTrafficPermitted="false">`.

### M-4 — Bogus permission declared "just in case" — **Low** — Fixed *(v2, v3)*

`AndroidManifest.xml` declared `android.permission.READ_CLIPBOARD`, which **is not a
real Android permission** — no such constant exists in the SDK. Clipboard reads require
no permission (they're gated at runtime by focus/IME status since Android 10). Android
ignores unknown permission strings, so it granted nothing, but it is exactly the kind of
speculative over-request that draws reviewer attention. Removed.

### M-5 — HTTPS scheme not enforced at the client — **Medium** — Fixed *(v2, v3)*

Both `APIClient`s built their URL by string-concatenating a developer-edited constant
(`WORKER_BASE_URL` / `BuildConfig.WORKER_BASE_URL`). A typo'd or pasted `http://` URL
would silently downgrade the connection. Added an explicit scheme assertion in both
clients so a non-HTTPS base URL fails loudly at the call site instead of transmitting a
screenshot in plaintext. Defence in depth behind M-3 and ATS.

### M-6 — iOS Full Access: justified, but onboarding copy was incomplete — **Medium** — Fixed *(v2)*

`RequestsOpenAccess: true` **is** strictly required — an iOS keyboard extension has no
network access at all without it, so the core feature cannot work otherwise. It is
correctly scoped: requested by the keyboard extension target only, not the container app.

However, the onboarding text asserted *"We NEVER log your keystrokes"* without telling
the user what the permission they are granting **technically allows**. Users see Apple's
alarming system warning and deserve the honest version. Rewritten to state plainly what
Full Access grants at the OS level, that MatchCraft's own use of it is the single network
call, and — since "trust us" is not a security control — how to verify independently.

### M-7 — Android permission set reviewed — **no over-request found**

| Permission | Used by | Verdict |
|---|---|---|
| `INTERNET` | `APIClient` (OkHttp) | Required |
| `SYSTEM_ALERT_WINDOW` | v3 bubble (`TYPE_APPLICATION_OVERLAY`) | Required |
| `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` | v3 `OverlayService` | Required (the second only on API 34+) |
| `READ_MEDIA_IMAGES` (API 33+) / `READ_EXTERNAL_STORAGE` (≤32) | `ScreenshotHelper` MediaStore query | Required, correctly version-gated |
| ~~`READ_CLIPBOARD`~~ | nothing | **Removed — not a real permission (M-4)** |

No `RECEIVE_BOOT_COMPLETED`, no location, no contacts, no camera, no
`QUERY_ALL_PACKAGES`, no `WRITE_EXTERNAL_STORAGE`.

**Every vulnerability found was in a build-time `devDependency`. None shipped to users.**
Both were fixed anyway, and both builds verified afterwards.

`kotlinx-coroutines` from Maven Central via a pinned version catalog

`URLSession` and UIKit only. No git URLs, no tarball URLs, no private or unpinned
registries anywhere. All versions are caret/exact-pinned and lockfiles are committed.

## 6. Abuse and cost control

**What now exists** (all in `enforceRateLimits`):

1. **Per-IP daily cap** — `RATE_LIMIT_MAX_PER_DAY`, default 10, keyed on
   `CF-Connecting-IP` only (unspoofable, W-4).
2. **Global daily circuit breaker** — `GLOBAL_DAILY_MAX`, default 500. A single counter
   across *all* callers. **This is the control that survives IP rotation.** Once the
   day's total is reached, every caller gets `429` until UTC midnight. Set it to a number
   you are genuinely willing to pay for in the worst case.
3. **Fail-closed** — no KV binding means `503`, not unlimited spend (W-3).
4. **Per-request cost bounds** — `max_tokens: 1024` caps output; the 5 MB image cap
   (W-5) bounds input.

Worst-case daily spend is therefore bounded by `GLOBAL_DAILY_MAX × (max input + 1024 output)`
tokens, rather than being unbounded as it was before this audit.

### ⚠️ Residual risks that are NOT closed

These are real and I am not going to claim otherwise:

- **IP-based limits are defeatable by anyone willing to rotate IPs.** A VPN, a proxy
  pool, mobile-network CGNAT, or IPv6 prefix rotation all yield fresh buckets. The
  global ceiling caps the *total damage* but cannot distinguish the attacker from your
  real users — so **an attacker who burns the global quota has denied service to
  everyone else for the rest of the day.** That DoS is the accepted trade-off for
  bounding cost without accounts. Closing it properly requires per-user identity
  (accounts, device attestation, or Cloudflare Turnstile), all out of scope for v1–v3.
- **Shared-IP collateral.** Users behind one office/university NAT share a bucket and
  may hit the cap through no fault of their own.
- **KV counters are eventually consistent and the increment is not atomic.** The
  read-then-write in `enforceRateLimits` is a TOCTOU race: a burst of concurrent requests
  can all read the same count and proceed, overshooting the limit. Cloudflare KV offers
  no atomic increment. Magnitude is bounded (roughly the concurrency of the burst, not
  unlimited), but it is a real overshoot. Closing it properly needs Durable Objects or
  the native Cloudflare Rate Limiting binding.
- **CORS is not access control** (W-1). Any non-browser client ignores it entirely.
- **No authentication of any kind.** The endpoint is deliberately open — that is the
  product decision ("no login required"), and it is the root cause of most of the above.
